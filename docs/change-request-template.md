# AgapSense Change-Control Template (Deliverable E)

Use this form **before** changing anything that is not an obvious typo. Baseline reference: [`system-specification.md`](system-specification.md) (current draft, v0.3), with [`scope-boundary-register.md`](scope-boundary-register.md) and [`requirements-traceability.md`](requirements-traceability.md).
Copy the template into an issue or `docs/changes/CR-NNN.md`; do not edit this file for individual requests.

## 1. Rules that always apply

1. Do not redesign existing behaviour only because an alternative is cleaner or more modern.
2. A bug fix preserves approved functionality and architecture wherever possible.
3. A defect in an existing feature does not authorise unrelated redesign or refactoring.
4. New functionality needs a documented requirement and explicit owner approval.
5. Database schema changes need a justified need, impact assessment and migration plan.
6. Changes to authentication, RLS, roles, device ownership or notification recipients need a security and regression review.
7. New integrations need justification, configuration requirements, failure handling and approval.
8. Changes to hardware, sensor thresholds, communication paths or detection logic need explicit review (they affect the physical prototype).
9. Do not change existing APIs, data contracts, route structures or component responsibilities unnecessarily. Contracts the firmware parses: `alert_event_id`, `owner_contact`, `bfp_contact`, `address_resolved`, `triggered_at`, `co_alert_ppm`, `temp_alert_c`, `owner_number`, `bfp_number`, `firmware_version`, `firmware_url`, `firmware_md5`; request fields it sends: `device_id`, `co_ppm`, `temp_celsius`, `latitude`, `longitude`, `gps_valid`, `on_battery`, `sensor_ready`, `battery_mv`, `rssi`, `mq7_phase`, `firmware_version`, `tier`, `alert_type`, and for SMS results `alert_event_id`, `role`, `success`.
10. Record unresolved questions in the Decision Register instead of answering them by assumption.

## 2. Classification decision tree

```
Is current behaviour contradicted by an owner-confirmed requirement or by the
spec's own "intended" text (§5.5/§5.9)?
 ├─ yes → BUG FIX (class 1)  — restore the documented behaviour only
 └─ no
     Is the capability already listed Included (class A) in the Scope Boundary Register
     and the request completes/finishes it as already described?
      ├─ yes → EXISTING-SCOPE WORK (class 2)
      └─ no
          Does it add a feature, role, channel, sensor, integration, page,
          data field, or change a threshold/recipient/auth rule?
           ├─ yes → SCOPE-EXPANDING CHANGE (class 3) — needs approval and a spec update
           └─ unsure → record as OQ-xx; do not start
```

*Items marked **Hold** or **Conflicting** in the register are not bug fixes until the linked decision is made.*

## 4. Minimum checklist before merge

- [ ] Classification agreed; if class 3, approval recorded.
- [ ] Spec, scope register and traceability matrix updated in the same change.
- [ ] No unrelated refactor; diff limited to what the request needs.
- [ ] Existing contracts unchanged, or additive and documented.
- [ ] Security/prototype reviews done where required.
- [ ] Tests run and results recorded; gaps declared (not claimed).
- [ ] Deployment order stated; nothing applied to production without approval.
- [ ] No secrets, phone numbers or keys in code, docs or logs.
